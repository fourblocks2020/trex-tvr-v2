# TVR requester-versioned GHCR 이미지 게시 계약

## Problem

`trex-tvr-v1`에는 검증 가능한 OCI runtime image와 requester가 선택한 stable SemVer tag에서만 동작하는 GHCR publication 계약이 없었다. Python dependency resolution, image build, isolated startup smoke, source·image·archive·registry provenance, 운영 mount와 rollback 경계를 저장소가 소유하지 않으면 동일 source라도 build 입력이 달라지거나 branch 검증이 registry write와 결합되고, publication 성공이 strategy·execution readiness 또는 production rollout 완료로 오해될 수 있다.

## Scope

- **create:** Python 3.12와 repository-owned `uv.lock`을 canonical baseline으로 삼고 package build dependency까지 고정한다.
- **create:** strict stable `vX.Y.Z` tag만 publication을 허용하고 branch/main/PR 검증과 registry write를 분리한다.
- **create:** exact source를 한 번 build한 image를 smoke·scan한 뒤 archive/checksum/image ID로 넘기며 publish 단계 rebuild를 금지한다.
- **create:** Git tag, `pyproject.toml` version, `trex_tvr.__version__`, OCI version label의 exact match와 source revision·image ID·archive SHA-256·registry digest provenance를 검증한다.
- **create:** synthetic canary가 image config/history/filesystem/archive/helper output에 남지 않는지 fail-closed 검사한다.
- **create:** isolated RabbitMQ AMQP login, Redis ping, fake kis-data-hub `/health`, TVR process startup과 initial status snapshot까지 publication smoke로 검증한다.
- **create:** runtime은 non-root `10001:10001`, read-only root filesystem, capability drop와 no-new-privileges를 사용하고 config·secret·status mount를 분리한다.
- **create:** immutable digest 실행·rollback, 기존 tag 비재생, bounded operator stop과 외부 state 비rollback 경계를 문서화한다.
- **release evidence:** GitHub 구현 진행·완료 comment를 정식 lifecycle 문서가 아닌 repository-local evidence snapshot으로 보존한다.

## Out of Scope

- strategy decision 또는 synthetic trex-core decision cycle 실행
- trex-core slot/intent RPC, intent delivery, KIS query, account access와 실제 주문
- strategy readiness, execution readiness, data freshness 또는 production readiness 보장
- 새 HTTP health endpoint 추가
- 새 SIGTERM handler 또는 graceful shutdown lifecycle 보장 추가
- tag 생성·push, GHCR publication, package visibility 변경, GitHub Release, production rollout·restart
- 외부 RabbitMQ·Redis·broker/order state 자동 rollback
- 이미 존재하는 Git tag를 삭제하거나 동일 이름으로 재생성하는 publication backfill

## Risks and Unknowns

### Risks

- Tag·package·runtime·OCI version이 불일치하면 잘못된 identity의 image가 게시될 수 있으므로 image build 또는 registry login 전에 fail-closed한다.
- Mutable base/smoke image 입력은 동일 source의 재현성을 훼손하므로 digest와 `linux/amd64` platform을 고정한다.
- Build archive 또는 helper output에 credential이 포함될 수 있으므로 synthetic canary로 context·image·archive·metadata·output을 검사하고 실제 credential은 사용하지 않는다.
- Process가 실행 중인 사실과 dependency readiness 및 strategy/execution readiness가 혼동될 수 있으므로 startup smoke와 보장하지 않는 항목을 명시적으로 분리한다.
- `docker stop --time 30`은 operator 절차이며 새 application-level SIGTERM 보장을 의미하지 않는다.

### Assumptions

- Requester가 release마다 새 stable SemVer를 별도로 선택하고 tag 생성·push 및 publication은 별도 승인을 거친다.
- 이미 존재하는 tag는 immutable provenance를 위해 삭제·재생성하지 않는다.
- Production rollout 전 운영 config, secret, dependency readiness와 status freshness는 publication smoke와 별도로 검증한다.

## 관찰된 `trex-tvr-v1` 현황

현재 `main` 기준:

- `pyproject.toml`에는 direct dependency range가 있으나 repository-owned `uv.lock`은 없다.

## 문제 정의

일반 `main` push마다 image를 게시하면 문서·governance-only 변경도 registry artifact를 생성하고 requester의 version/release 선택과 publication이 분리된다. 반대로 Docker build 성공만으로 전략 daemon이 운영 가능한 artifact라는 보장도 없다.

`trex-tvr-v1`은 다음을 동시에 만족해야 한다.

1. publication authority가 requester가 선택한 strict version tag에만 귀속될 것
2. repository verification과 runtime dependency가 동일한 lock resolution을 사용할 것
3. verify job에서 시험한 exact image만 publish job으로 전달되고 rebuild되지 않을 것
4. source commit, image ID, archive checksum, OCI revision과 registry digest가 연결될 것
5. RabbitMQ·Redis·kis-data-hub credential 및 strategy config가 build context, layer, history, archive와 metadata에 포함되지 않을 것
6. installed image에 `trex_tvr`, `trex-tvr`, `trex-tvr-backtest`와 필요한 config/runtime resources가 존재할 것
7. process liveness, dependency readiness와 strategy decision correctness를 구분할 것
8. image rollback과 strategy state·core execution state rollback을 구분할 것
9. publication이 실제 주문·production rollout 승인으로 오해되지 않을 것

## 제안 방향

publication·공급망 계약은 portfolio-hub #25의 완료된 방식과 동일하게 채택하고 smoke를 TVR runtime에 맞춘다.

### 공통 publication 계약

- strict stable `vX.Y.Z` Git tag push만 publication event로 허용
- `main`, 일반 branch, PR, `workflow_dispatch`, malformed/prerelease tag에서는 registry write 금지
- 자동 version 증가와 moving `latest` 금지
- exact tagged commit checkout 및 checked-out HEAD 일치 검증
- repository-owned `uv.lock`을 만들고 pinned `uv` + locked CI/runtime install 사용
- branch/main에서 registry write 없이 full pytest와 release/container contract 검증
- source image는 한 번만 build
- OCI full revision, tested image ID와 exported archive SHA-256 기록
- synthetic canary를 build context, filesystem, history, inspect metadata, archive와 helper output에서 검사
- publish job은 checksum/image ID/revision을 확인한 동일 archive를 load하고 rebuild 없이 게시
- 다음 selector만 부여하고 동일 registry digest를 검증
  - `ghcr.io/fourblocks2020/trex-tvr-v1:<source-commit-first-12>`
  - `ghcr.io/fourblocks2020/trex-tvr-v1:vX.Y.Z`
- 운영 정본은 `ghcr.io/fourblocks2020/trex-tvr-v1@sha256:<digest>`
- linux/amd64, non-root fixed UID/GID, read-only root filesystem을 기본 계약으로 사용
- config/status/cache가 필요한 경우에만 명시적인 read-only secret/config mount와 writable path를 분리

### `trex-tvr-v1` 전용 verification

1. **Installed payload smoke**
   - networkless/read-only/non-root container에서 `python -I -c 'import trex_tvr'`, `trex-tvr --help`, `trex-tvr-backtest --help` 검증
   - package version, CLI version과 strict Git tag version 정합 확인
2. **Configuration fail-closed smoke**
   - secret 없이 image를 검사하고 synthetic config만 runtime에 주입
   - malformed/missing required config는 credential을 출력하지 않고 명확하게 실패
   - source checkout path나 editable install에 의존하지 않음을 검증
3. **Isolated dependency readiness smoke**
   - internal network에서 synthetic RabbitMQ, Redis와 deterministic fake kis-data-hub `/health`만 사용
   - startup gate가 세 dependency 정상 시 통과하고 각 dependency 장애 시 fail-closed하는지 구분 검증
   - production endpoint, account, token, KIS credential과 실제 주문 사용 금지
4. **Dependency startup smoke와 initial status**
   - internal network의 synthetic RabbitMQ·Redis·fake kis-data-hub로 실제 startup dependency gate를 검증
   - non-root/read-only process startup과 initial status snapshot을 확인하되 strategy decision cycle, trex-core slot/intent RPC, intent delivery와 실제 주문은 publication smoke에서 주장하지 않음
   - broker outcome/retryability event를 TVR에 주입하지 않음
   - container/network/temporary resource의 exact cleanup까지 PASS 조건에 포함
   - 새 SIGTERM lifecycle 보장을 추가하지 않고 orchestrator bounded stop과 마지막 status/log 보존 경계를 문서화
5. **Artifact handoff·live read-back**
   - tested archive를 publish job에서 no-rebuild load
   - version/source selectors, platform, non-root user, OCI source/revision/version와 immutable digest를 GHCR에서 재확인
   - hosted workflow 성공과 GHCR publication은 증거화하되 production rollout 완료로 표현하지 않음
