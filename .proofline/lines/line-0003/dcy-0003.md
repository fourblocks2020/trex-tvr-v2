# RabbitMQ Transport Reliability / Resilience

## Problem

2026-07-24 운영에서 TVR RabbitMQ connection reset과 `StreamLostError`가 반복됐고, 이후 Supervisor 및 dependency snapshot이 회복됐더라도 장시간 idle, request publish 중 단절, reply 유실, broker restart 뒤 RPC 신뢰성은 입증되지 않았다. TVR의 실제 runtime surface는 authoritative slot snapshot RPC와 intent admission RPC이며, TSL alarm/fill event 및 broker execution lifecycle은 별도 ownership 경계다.

## Scope

- **create:** TVR typed config가 heartbeat 30초, blocked connection timeout 30초, socket timeout 10초의 기본값·override validation을 소유하고 RabbitMQ URL의 같은 tuning key 중복은 startup에서 fail-closed한다.
- **create:** Slot RPC와 intent admission RPC 모두 publisher confirm을 사용하되 RabbitMQ broker acceptance를 core admission·주문·체결 완료와 구분한다.
- **create:** Daemon cadence idle 동안 BlockingConnection의 AMQP I/O와 heartbeat를 처리하고 reset/restart 뒤 bounded reconnect 및 dependency status recovery를 제공한다.
- **create:** Intent reply 유실의 ambiguous outcome에서 fresh/local retry intent를 만들지 않고 reconnect 후 authoritative core slot snapshot을 먼저 조회해 수렴한다.
- **create:** Unit 및 disposable RabbitMQ 장애 주입으로 idle, forced disconnect, broker restart, reconnect, buy/sell no-duplicate convergence를 검증하고 secret을 노출하지 않는다.
- **release evidence:** GitHub의 구현 진행·완료 comment를 정식 ProofLine lifecycle artifact가 아닌 repository-local evidence snapshot으로 보존한다.

## Risks and Unknowns

### Risks

- Publisher confirm을 core admission으로 오해하면 reply 유실 시 lifecycle을 잘못 판단할 수 있다.
- Ambiguous timeout 뒤 fresh intent ID를 즉시 제출하면 중복 주문 위험이 있다.
- BlockingConnection cadence 대기 중 AMQP I/O를 처리하지 않으면 heartbeat 30초 profile과 60초 cadence가 충돌할 수 있다.
- Mock-only 검증은 socket reset과 broker restart를 입증하지 못한다.
- URL과 typed config가 동시에 tuning을 소유하면 precedence drift가 발생하므로 중복을 거부해야 한다.

### Assumptions

- Reconnect 후 core slot RPC snapshot은 TVR의 authoritative reconciliation input이다.
- Core가 durable intent log, dedup, slot transition과 broker execution lifecycle을 계속 소유한다.
- 이 문서는 승인된 specification과 repository-local 구현 평가를 정리하며 release, deployment 또는 terminal lifecycle closure를 주장하지 않는다.

> ## Problem
>
> 2026-07-24 TREX 전략 daemon에서 RabbitMQ transport reset이 발생했다. 당시 `trex-tvr-v1`에는 connection reset 및 `StreamLostError` 이후 retry가 관찰됐고, 운영 보고상 당일 transport 관련 오류가 12건이었다. `trex-tsl-v1`에서도 09:15 KST에 `ConnectionResetError`·`StreamLostError`와 alarm emit failure가 관찰됐다.
>
> Supervisor와 TVR dependency snapshot은 이후 `RUNNING` / RabbitMQ `ok` 상태로 회복됐지만, 일시적 회복만으로 장시간 idle, request publish 중 연결 단절, reply 유실 또는 broker restart 이후의 지속적인 RPC 신뢰성을 입증할 수 없다.
>
> 현재 이슈는 TVR의 slot/intent RPC transport 문제와 TSL alarm failure, fill/alarm event 신뢰성 및 DLQ 정책을 함께 언급한다. 그러나 현재 TVR은 RabbitMQ RPC로 slot snapshot을 조회하고 intent admission을 요청하며 broker/fill event나 alarm event를 publish·consume하지 않는다. 따라서 구현 전에 repository 범위, transport 대상, ambiguous intent outcome 처리, connection tuning authority와 장애 검증 수준을 결정해야 한다.
