# buy를 decision-scoped 멱등 ID로 전환

## Problem

현재 TVR buy intent의 `intent_id`는 `strategy`, `instance`, 거래일, `slot`만 포함해 같은 거래일·같은 slot의 서로 다른 strategy decision을 하나의 논리 intent로 취급한다. 따라서 최초 buy가 pre-broker 사유로 거절된 뒤 authoritative core slot snapshot과 안전 조건이 바뀌어도 다음 cycle은 같은 ID를 제출하고, core는 과거 결정을 멱등 재사용할 수 있다.

또한 daemon은 core가 buy를 `admitted`한 `(instance, slot)`을 프로세스 수명의 `_admitted_slots`에 보관하고 같은 거래일의 후속 buy 평가를 `reentry_skip`한다. 주문 완료 후 slot이 다시 `holding`으로 수렴하고 최신 수량·현금·가격·전략 비중이 추가 buy 조건을 충족하더라도 이 local guard가 authoritative snapshot에 따른 독립 재평가를 차단한다.

기대 상태는 buy도 sell과 같은 decision-scoped identity 계약을 사용해 동일 decision의 transport 중복과 이후 snapshot에서 발생한 독립 decision을 구분하는 것이다. 후속 buy 가능 여부는 daemon-local 일 단위 이력이나 broker outcome이 아니라 최신 authoritative core slot snapshot과 현재 전략 조건으로 결정해야 한다.

## Scope

- **create:** Buy intent ID를 정확히 `buy:{strategy}:{instance}:{date}:{slot}:{decision_at}` 형식으로 정의한다. `decision_at`은 현재 authoritative core slot snapshot을 평가한 strategy decision cycle에서 생성하며 broker result, retryability 또는 attempt identity에서 만들지 않는다.
- **create:** 동일 buy decision payload의 transport 중복은 동일 ID를 사용하고, 이후 새 authoritative snapshot에서 발생한 독립 buy decision은 같은 거래일·같은 slot이어도 새 ID를 사용한다. `decision_at` 부재는 builder에서 fail-fast한다.
- **create:** Buy와 sell 모두 방향 namespace를 유지해 core의 `intent_id` 단독 key 공간에서 충돌하지 않게 하고, RabbitMQ `correlation_id == payload.intent_id` 계약을 유지한다.
- **create:** 프로세스 수명·거래일 단위 `_admitted_slots` 및 `reentry_skip` 차단을 제거한다. Buy admission 또는 rejection 이력 자체가 이후 `(instance, slot)` 판단을 차단하지 않으며, 최신 snapshot의 수량·현금·가격·전략 비중이 buy 조건을 충족할 때만 새 decision과 RPC를 만든다.
- **create:** `pending_buy`와 `pending_sell` snapshot에서는 신규 buy를 만들지 않고, 주문 완료 후 `holding`으로 돌아온 snapshot은 독립적으로 재평가할 수 있음을 회귀 검증한다. `reconcile_warned` 등 pre-broker rejection 뒤 경고가 해제된 `holding` snapshot도 새 decision ID로 재평가할 수 있어야 한다.
- **satisfy (`ac-0003`):** 후속 buy 판단은 broker/fill event가 아니라 authoritative core slot snapshot만 사용해 기존 snapshot-only execution ownership 경계를 변경 없이 충족한다.
- **satisfy (`ac-0015`):** timeout/reset/reply 유실의 ambiguous outcome에서 즉시 새 `decision_at`으로 blind retry하지 않고 reconnect 후 snapshot-first로 수렴하는 기존 의미를 유지한다.
- **unchanged regression (`ac-0004`):** 기존 sell decision ID 형식, snapshot-only 독립 후속 판단과 fail-fast 계약은 변경하지 않는다.
- 관련 builder, daemon, transport wire/import seam, 문서와 전체 TVR 회귀 검증을 포함한다. 실제 cutover 전에는 old-format intent, 현재 slot, pending order와 broker lifecycle을 감사할 수 있는 배포 전 확인 기준을 남긴다.

## Out of Scope

- `trex-core`의 `intent_id` PK, dedup, admission wire schema, slot lifecycle 또는 DB schema 변경
- 기존 core `intent_log` 행의 삭제·수정·재평가
- Broker 자동 retry, broker failure/retryability event 구독 또는 attempt identity 도입
- 기존 sell decision-scoped identity 및 snapshot-only 계약의 의미 변경
- 운영 배포, 장중 cutover 실행, production 설정 변경 또는 실제 주문
- Release publication과 기존 감사 기록 삭제

## Risks and Unknowns

### Risks

- Reply 유실·timeout·reset 뒤 이를 새 strategy decision으로 오인해 fresh `decision_at`을 만들면 core가 이미 수락한 buy와 중복 주문이 발생할 수 있다. Snapshot-first 수렴과 `pending_*` gate를 함께 검증해야 한다.
- `_admitted_slots` 제거 후 `holding` snapshot마다 무조건 새 ID를 만들면 불필요한 admission 요청이나 추가매수가 발생할 수 있다. ID 생성과 RPC 호출은 최신 전략 계산이 실제 buy 조건을 충족한 뒤에만 수행해야 한다.
- 새-format ID는 기존 day/slot key와 다르므로 장중 전환 시 old-format admitted intent 또는 pending order와 동일한 논리 buy가 새 ID로 재제출될 수 있다. 기본 cutover는 다음 거래일 시작 전으로 제한하고, 장중 전환은 명시적 상태 감사를 요구한다.
- 같은 decision의 transport 재전송과 다음 snapshot cycle의 독립 decision 경계가 구현에서 분리되지 않으면 멱등성과 후속 재평가 중 하나가 깨질 수 있다.
- 현재 `tests/runtime/test_daemon_cycle.py:243-260`은 제거 대상인 `reentry_skip`을 정답으로 단언하므로 요구사항 변경 시 반대 방향 회귀 테스트로 교체해야 한다.

### Assumptions

- Core slot RPC snapshot은 buy 후속 판단과 ambiguous outcome 수렴의 authoritative input이다.
- Core는 `intent_id`를 opaque idempotency key로 계속 처리하고 durable intent log, slot transition과 broker lifecycle을 소유한다.
- Issue #12 본문의 결정된 형식·범위·수용 기준은 Discovery 초안의 source이며, 이 draft의 confirmation은 별도 사용자 승인 전까지 부여되지 않는다.
